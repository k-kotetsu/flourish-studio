# ADR-001 データベースの選定：DynamoDB と PostgreSQL の比較

> 作成：2026-08-08
> 状態：**採用**（2026-08-08 決定）
> 反映先：`08_データモデル/logical-data-model.md` Version 0.3、`11_技術構成/tech-architecture.md` Version 0.3

---

## 1. 論点

`11_技術構成` 0.2 では Aurora Serverless v2（PostgreSQL）を採り、最小0 ACU・単一AZ・RDS Proxy廃止で月約$20まで下げた。**これをさらに下げられるか、DynamoDB と比較する。**

固定費全体が月約$36であり、そのうちDBが$20とNATが$4を占める。**DBの選択が固定費の3分の2を決めている。**

---

## 2. この製品のアクセスパターン

**比較の前に、実際に何を問い合わせるのかを洗い出す。** 一般論ではなく、`09_API設計` 4章の25エンドポイントから機械的に導く。

| # | 操作 | 問い合わせの形 |
|---|---|---|
| 1 | `GET /home` | 1ユーザーの現行 Purpose ＋ 4領域の AreaPlan ＋ 目標数 |
| 2 | `GET /assessments/{id}` | 1レポートとその結果一式 |
| 3 | `GET /purposes/current` | 1ユーザーの現行 Purpose |
| 4 | `PUT /purposes/current` | 新バージョン作成＋旧行の `is_current` を false |
| 5 | `POST /purposes` | Purpose ＋ 選択式 ＋ 対話全文をまとめて保存 |
| 6 | `POST /area-plans` | AreaPlan ＋ 選択式 ＋ 対話 ＋ 目標1〜3をまとめて保存 |
| 7 | `GET /area-plans/{area}` | 1ユーザー・1領域の現行版 |
| 8 | `GET /reflections/context` | 1ユーザーの現行目標一覧 |
| 9 | `POST /reflections` | 回答 ＋ AI出力をまとめて保存 |
| 10 | `GET /jobs/{id}` | ID指定で1件 |
| 11 | 認証・セッション | 不透明ID指定で1件 |
| 12 | レート制限 | カウンタの原子的な加算 |
| 13 | 冪等性 | キーの条件付き挿入 |
| 14 | 記事 | カテゴリ別の一覧（静的生成時のみ） |

**この一覧には、以下が1つも存在しない。**

- 複数ユーザーをまたぐ問い合わせ
- 全文検索
- 動的な条件による絞り込み
- 3つ以上のエンティティにまたがる結合

理由は設計側にある。`user-flow` 2章の「確定した成果物だけを保存する」という決定が、**保存単位を集約（アグリゲート）として綺麗に切り分けた。** 入力途中はクライアントが持ち、サーバは完成品だけを1トランザクションで書く。この形は、そのままDynamoDBの単一テーブル設計に乗る。

## 3. エンティティごとの適合度

| エンティティ群 | DynamoDBへの適合 | 備考 |
|---|---|---|
| `SESSION` / `GUEST_SESSION` | **◎** | 不透明IDで1件引くだけ。**TTLで30日削除が無料**（PostgreSQLでは定期削除ジョブが要る） |
| `JOB` | **◎** | ID指定の読み取りのみ。**TTLで7日削除が無料** |
| `IDEMPOTENCY_KEY` | **◎** | 条件付き書き込みがそのまま冪等性になる。TTLで24時間削除 |
| `RATE_LIMIT_COUNTER` | **◎** | `UpdateItem` の `ADD` で原子的加算。TTLで時間枠を自動失効 |
| `CURRENT_STATE_ASSESSMENT` 一式 | **○** | 選択式24・自由記述8・結果を**1アイテムに内包できる**（後述） |
| `PURPOSE` ＋ 選択式 ＋ 対話 | **○** | 同上 |
| `AREA_PLAN` ＋ 選択式 ＋ 対話 ＋ 目標 | **○** | 同上 |
| `WEEKLY_REFLECTION` 一式 | **○** | 同上 |
| `USER` | **○** | Cognito の `sub` で引く。メール一意性はCognitoが担保する（`11_技術構成` 7.2） |
| `AI_GENERATION` | **△** | 集計（`kind` ごとの失敗率など）ができない。**CloudWatch EMF に出すほうが本来正しい** |
| `ARTICLE` | **△** | 数百件。カテゴリ別一覧はGSIで足りる。**将来のレコメンドは検索の問題であり、どちらのDBでも別手段が要る** |

### 3.1 アイテムサイズの確認

DynamoDBの1アイテム上限は400KB。最も大きい `CURRENT_STATE_ASSESSMENT` を見積もる。

| 内容 | 概算 |
|---|---|
| 選択式24問（コードとスコア） | 約 1KB |
| 自由記述8問（1問あたり上限1,000文字・UTF-8） | 約 24KB |
| 生成された問い文8件 | 約 3KB |
| あだ名 ＋ 4領域 × 3ブロック | 約 5KB |
| **合計** | **約 33KB** |

**上限に対して1桁以上の余裕がある。** 集約を1アイテムにまとめても破綻しない。

### 3.2 バージョン管理の扱い

`08_データモデル` 4.1 は「編集は上書きではなく新しい行の追加」「`is_current = true` はユーザーごとに1件」と定めている。

DynamoDBでは次のように置き換える。

```text
PK = USER#<user_id>
SK = PURPOSE#CURRENT          ← 現行版（1件しか存在しえない）
SK = PURPOSE#V#000001         ← 過去版
SK = PURPOSE#V#000002
```

**「現行版は1件」を、キーの形そのもので保証する。** `is_current` フラグを持って一意制約で守るより、むしろ壊れにくい。更新は `TransactWriteItems` で「旧CURRENTを版番号付きにコピー」「新CURRENTを書く」を1トランザクションにする。

`goal_key` による系列追跡（データモデル4.2）はGSIで対応する。

## 4. コスト比較

### 4.1 前提

新規100人／月、継続100人（週1回の振り返り）、累計1,000人。

### 4.2 DynamoDB の見積もり

| 項目 | 量 | 月額 |
|---|---|---|
| 書き込み | 約 10,000 WRU | **$0.02** |
| 読み取り（**ジョブのポーリングが大半**） | 約 55,000 RRU | **$0.02** |
| ストレージ | 約 60MB | **$0.02** |
| PITR（継続的バックアップ） | 約 60MB | **$0.02** |
| **合計** | | **月 $1 未満** |

最大の読み取り要因は生成中画面のポーリング（1ジョブあたり約40回）だが、**この規模では誤差**である。1,000人規模に10倍しても月$1〜2に収まる。

### 4.3 3案の比較

| 項目 | Aurora Serverless v2<br/>（現行の0.2案） | RDS t4g.micro | **DynamoDB** |
|---|---|---|---|
| DB本体 | 約 $20 | 約 $14 | **約 $1** |
| NATインスタンス | $4 | $4 | **$0（不要）** |
| **DB関連の月額** | **約 $24** | **約 $18** | **約 $1** |
| ユーザー0人のとき | 約 $5（停止時） | 約 $14 | **約 $0** |
| 1,000人＋1,000人のとき | 約 $60〜90 | **上限に当たる** | 約 $2 |

**NATが不要になる理由は4.4で述べる。これが2つ目の削減になる。**

### 4.4 VPCが不要になる

Aurora はVPC内に置く必要があり、そのためLambdaもVPCに入る。すると外部（Cognito・Google OAuth・Bedrock）へ出るためにNATが要る。

**DynamoDBはVPCを必要としない。** IAM認証のAPIとして呼ぶため、Lambdaを非VPCで動かせる。結果として次が同時に消える。

| 消えるもの | 効果 |
|---|---|
| NATインスタンス | **月$4の削減。および `11_技術構成` 14章のリスク#6（単一障害点）が消える** |
| `NetworkStack` | CDKのスタックが1つ減る |
| VPC内Lambdaのコールドスタート | ENI割り当てが不要になり、初回起動が速くなる |
| Aurora自動停止の15秒（リスク#7） | **消える** |
| 予約同時実行によるDB接続数の管理（6.3） | 不要になる。同時実行を自由に増やせる |

**コスト以上に、構成が単純になる効果が大きい。** `11_技術構成` の6章・9章・10章がまとめて短くなり、リスク一覧から2件消える。

## 5. DynamoDB で失うもの

**ここが判断の本体である。** コストだけを見れば結論は明らかで、問題は代償を受け入れられるか。

| # | 失うもの | 深刻さ |
|---|---|---|
| 1 | **場当たりのSQL** | **最大の代償。** 「言語化度の分布は」「どの領域から始める人が多いか」といった問いに、その場で答えられなくなる |
| 2 | スキーマ変更の道具 | Alembic 相当がない。構造を変えるときは全アイテムの移行スクリプトを書く |
| 3 | 宣言的な制約 | 外部キー、一意制約、CHECK が使えない。**アプリが守る**（3.2のように、キー設計で代替できるものもある） |
| 4 | 将来のレコメンド | `08_データモデル` 1章は記事をDBに置く理由を「領域や項目と紐づけて検索する」としている。DynamoDBでは苦しい |
| 5 | 集計 | `AI_GENERATION` の失敗率などが集計できない |
| 6 | 学習コスト | 単一テーブル設計は、SQLと同じようには書けない |

### 5.1 #1（場当たりのSQL）への評価

**MVPの目的は検証である。** `02_MVP範囲定義` は「一連の体験が価値として成立するか」を検証したいとしている。その判断には、想定していなかった角度からデータを見る場面が必ず来る。

ただし、既存の設計は**既に分析の多くを諦めている。**

- `08_データモデル` 11.1：提示した3案のうち選ばれなかった2案を保存しない → 3案の軸が機能しているか測れない
- `08_データモデル` 11.2：入力途中を保存しない → 途中離脱の分析ができない

**追加で諦めることになるのは「保存してあるデータへの自由な問い合わせ」であり、これは緩和できる。**

| 緩和策 | 内容 |
|---|---|
| **S3エクスポート ＋ Athena** | DynamoDBはPITRからS3へエクスポートできる。**SQLで分析できる**。月次でよい |
| GSIの追加 | 想定できる分析軸は後からGSIを足せる |

### 5.2 #4（レコメンド）への評価

MVP対象外（定義書12.2）であり、そもそも**カテゴリ一致だけの単純な出し分けでは価値が出ない**機能である。本格的にやるなら、PostgreSQLでもDynamoDBでも検索基盤（OpenSearch等）が別途要る。**DBの選択で決着する話ではない。**

記事はMVPで静的生成しており（`11_技術構成` 4.4）、数百件規模である。**記事だけPostgreSQLに残す、あるいはS3のJSONで持つ**選択肢もある。

### 5.3 #5（集計）への評価

**これはむしろDynamoDBが正しい設計を強制する。** `AI_GENERATION` は運用データであり、失敗率やトークン数の監視は**CloudWatch のメトリクスに出すべきもの**である。DBに入れて後から集計するのは、本来の置き場所ではない。

`11_技術構成` 11.2 のダッシュボードは、EMF（埋め込みメトリクス形式）でログに出せばそのまま作れる。

|---|---|

## 7. 推奨

**DynamoDB を採ることを推奨する。**

理由を優先順に挙げる。

1. **アクセスパターンが完全に列挙でき、そのすべてが単一ユーザー・単一集約に閉じている**（2章）。DynamoDBが苦手とする問い合わせが1つも存在しない
2. **月$24 → 月$1。** 固定費全体が約$36から**約$13**になる
3. **VPCが不要になり、リスクが2件消える**（4.4）。コスト以上にこちらの効果が大きい
4. 失うものの筆頭（場当たりのSQL）は、**S3エクスポート＋Athenaで実用上は埋められる**（5.1）
5. 未着手のため、書き直しは文書のみで済む（6章）

### 7.1 採らない場合の次善

**`08_データモデル` を書き直す時間を取れない場合、RDS t4g.micro に切り替える。** Aurora Serverless v2 より月$6安く、自動停止の15秒（リスク#7）も消える。ただしNATは残るため、DB関連は月$18で下げ止まる。

| 案 | DB関連の月額 | 文書の書き直し |
|---|---|---|
| **DynamoDB** | **約 $1** | `08` 全面 ＋ `11` の5章分 |
| RDS t4g.micro | 約 $18 | `11` の6章のみ |
| Aurora Serverless v2（現行） | 約 $24 | なし |

### 7.2 採らない判断が妥当な場合

以下に当てはまるなら、PostgreSQLを維持すべきである。

- 検証期間中、**日常的にデータを触って仮説を立てたい**（月次のAthenaでは遅い）
- 単一テーブル設計の経験がなく、**学習に時間を割けない**
- MVP後すぐにレコメンドを実装する予定がある

## 8. 採用した場合の設計方針（概略）

書き直しの規模感を示すための素描であり、確定仕様ではない。

### 8.1 テーブル構成

**単一テーブル `flourish` ＋ GSI 2本。**

| キー | 内容 |
|---|---|
| PK | `USER#<id>` / `GUEST#<id>` / `JOB#<id>` / `SESSION#<token>` など |
| SK | `PROFILE` / `PURPOSE#CURRENT` / `AREA#CAREER#CURRENT` / `ASSESSMENT#<id>` など |
| GSI1 | `goal_key` による系列追跡（データモデル4.2） |
| GSI2 | 記事のカテゴリ別一覧 |

### 8.2 主要な操作

| 操作 | 実装 |
|---|---|
| `GET /home` | `Query(PK = USER#id, SK begins_with ...)` の1回で Purpose と4領域を取得 |
| `POST /area-plans` | `TransactWriteItems`（AreaPlan・目標・対話をまとめて） |
| `PUT /purposes/current` | `TransactWriteItems`（旧CURRENTを版番号付きへ、新CURRENTを書く） |
| 冪等性 | `PutItem` ＋ `attribute_not_exists(PK)` |
| レート制限 | `UpdateItem` ＋ `ADD` ＋ 条件付き |
| 有効期限つきデータ | **TTL属性。削除ジョブを書かない** |

### 8.3 論理削除

`08_データモデル` 10.1 の「物理削除しない」は、`deleted_at` 属性で同様に実装する。**TTLは設定しない**（TTLは物理削除であり、方針に反する）。

TTLを使うのは `SESSION` / `GUEST_SESSION` / `JOB` / `IDEMPOTENCY_KEY` / `RATE_LIMIT_COUNTER` の5つに限る。**いずれも保持期間が明示的に決まっており**（API設計8章、データモデル10章）、内面の記録ではない。

## 9. 決定

**DynamoDB を採用した（2026-08-08）。**

| 反映先 | 内容 |
|---|---|
| `08_データモデル` Version 0.3 | 単一テーブル設計に全面書き直し。業務ルールは引き継ぎ |
| `11_技術構成` Version 0.3 | 6章（DB）、9章（VPC廃止）、10章（スタック）、12章（コスト）、14章（リスク）を更新 |

### 9.1 実際の効果

| 項目 | 見込み | 実装後の記載 |
|---|---|---|
| DB関連の月額 | $24 → $1 | 同じ |
| 固定費全体 | $36 → 約$13 | 同じ |
| 消えたリスク | 2件（NAT単一障害点、DB再開15秒） | **加えて「Aurora単一AZのAZ障害」も消えた**（DynamoDBは複数AZに自動複製されるため） |
| 消えたもの | − | `NetworkStack`、RDS Proxy、DB認証情報、接続数管理、削除ジョブ、Alembic |

**見込みになかった副次的な効果が2つあった。**

1. **可用性が上がった。** コスト削減と引き換えに単一AZを受け入れていたが、DynamoDBは標準で複数AZに複製される。Auroraで同等の可用性を得るにはMulti-AZで月$45以上かかる
2. **管理するシークレットが減った。** DB接続文字列という、漏れたときの影響が最も大きい種類のものが消えた

### 9.2 引き継いだ設計上の負債

| 項目 | 対応 |
|---|---|
| 場当たりのSQLが使えない | S3エクスポート＋Athena。**リリース前に一度通す**（技術構成6.5） |
| 制約の担保がアプリに移った | リポジトリ層を1箇所に集約。ユニットテストの比重を上げる（データモデル12.4） |
| スキーマ変更に移行スクリプトが要る | 属性の削除・意味の変更をしない運用で回避する（技術構成6.3） |
