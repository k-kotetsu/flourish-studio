## 1. 解くべき問題

ドキュメントは12本・約17万字（**約12万トークン**）ある。

| ドキュメント | 字数 |
|---|---|
| `10_AIプロンプト設計` | 33,290 |
| `11_技術構成`（本体＋ADR） | 35,342 |
| `08_データモデル` | 21,174 |
| `05_質問・コンテンツ設計` | 13,719 |
| `09_API設計` | 13,306 |
| `01_全体コンセプト` | 12,619 |
| `04_画面設計` | 12,489 |
| `07_デザイン原則` | 11,716 |
| `06_ワイヤーフレーム` | 11,089 |
| `03_ユーザーフロー` | 6,857 |
| `02_MVP範囲定義` | 1,977 |

**全部読ませると、1タスクに実際に関係するのは5〜10%である。**

問題はコストより**注意の分散**にある。12万トークンのうち11万トークンが無関係な状態では、守るべき規則が埋もれる。「Primaryは1画面に3箇所まで」も「退会は論理削除のみ」も、同じ重みで流れていく。

### 目標

| 項目 | 目標 |
|---|---|
| 常時ロード | **2,000トークン以内** |
| 1タスクの実効 | **15,000〜25,000トークン** |
| 1タスクあたりの入力コスト | Sonnet 5 で **$0.05〜0.08**（キャッシュなし） |

## 2. 3層構造

```
常時ロード（約1,800トークン）
├── CLAUDE.md                    製品の一行説明、破ってはいけない規則7つ、
│                                ドキュメントの地図、スタック、コマンド
└── スキルの description × 5     いつ呼ぶかだけ（各約40トークン）

オンデマンド（呼ばれたときだけ・各2,000〜4,000トークン）
└── .claude/skills/*/SKILL.md    決定と規約を蒸留したもの

タスクごと（backlog.md の「参照」で指定・5,000〜15,000トークン）
└── docs/**/*.md の該当章        全文の仕様
```

### 層の役割分担

| 層 | 内容 | 判断基準 |
|---|---|---|
| CLAUDE.md | **忘れると事故になること** | 破ると仕様違反になる規則、地図 |
| スキル | **毎回同じ判断をすること** | 「この色でいいか」「このキーでいいか」 |
| ドキュメント | **そのタスクだけで要ること** | 質問文の中身、画面レイアウト、プロンプト全文 |

**スキルはドキュメントの写しではない。** ドキュメントは「なぜそう決めたか」を含み、スキルは「どうすればいいか」だけを持つ。理由が要る場面では、スキルの末尾にある出典を辿る。

## 3. スキル一覧

| スキル | 発動する作業 | 蒸留元（字数） | スキル |
|---|---|---|---|
| `flourish-tone` | ユーザーに見える日本語を書く | `07` 8章＋`01` 14章＋`10` 3.2 | **2,044字** |
| `flourish-ui` | Vue／CSS を書く | `07` 全文（11,716字） | **4,682字** |
| `flourish-data` | DynamoDB に触れる | `08` 全文（21,174字） | **4,605字** |
| `flourish-api` | エンドポイントを追加・変更 | `09` 全文（13,306字） | **5,699字** |
| `flourish-ai` | Bedrock 呼び出し・プロンプト | `10` 2〜3章（33,290字の一部） | **4,945字** |

**蒸留率はおよそ 1/3〜1/5。** `flourish-data` は21,174字を4,605字にしている。落としたのは「なぜそう決めたか」と完全なJSON例で、**判断に必要な規則は落としていない。**

### 常時ロードの実測

| 項目 | 字数 | 概算トークン |
|---|---|---|
| `CLAUDE.md` | 2,158 | 約 1,510 |
| スキルの `description` × 5 | 827 | 約 580 |
| **合計** | **2,985** | **約 2,090** |

**目標の2,000トークンをわずかに超えるが、許容範囲とする。** これ以上削ると `CLAUDE.md` の「破ってはいけない規則」を減らすことになり、本末転倒になる。

### なぜこの5つか

**横断的で、かつ毎回同じ判断をするもの**を選んだ。

| 選んだ | 理由 |
|---|---|
| tone | **最も頻出。** UI文言・エラー文・プロンプトのすべてに効く |
| ui | 色とコントラストは間違えると事故。トークン表を毎回引く |
| data | キー設計を間違えると後から直せない |
| api | Cookie・エラー形式・ジョブの型が全エンドポイントで同じ |
| ai | パラメータの禁止事項（`temperature` で400）を忘れると動かない |

### 作らなかったもの

| 候補 | 理由 |
|---|---|
| `flourish-screen`（画面IDの索引） | **画面仕様はタスク固有。** バックログの「参照」で足りる |
| `flourish-test` | テストの書き方に製品固有の判断がほとんどない |
| `flourish-cdk` | CDKを書くのは P1 の数タスクだけ。スキルにするほど反復しない |

**スキルを増やすと description の常時コストが増える。** 反復しない知識はドキュメントに置く。

## 4. 画面IDが索引になっている

全ドキュメントで画面ID（`S-16`、`K-01` など）が共通の見出しになっている。

```bash
grep -rn "S-16" docs/
```

これで、画面設計・ワイヤーフレーム・質問コンテンツ・API設計・データモデル・プロンプト設計の該当箇所が一度に揃う。**バックログの「参照」は、この grep を先回りして書いたものである。**

## 5. セッションの型

### 開始時

```
P2-3 を実装します。
参照：docs/05_質問・コンテンツ設計 2章、docs/06_ワイヤーフレーム
スキル：flourish-ui
```

**タスクIDを宣言させる。** これにより読む範囲が固定され、脱線が減る。

### 実装中

- 仕様に書かれていないことが出てきたら**止めて聞く**
- 仕様の矛盾を見つけたら**実装前に報告する**

### 終了時

```bash
make lint && make test
```

完了条件を満たしたら `backlog.md` にチェックを入れる。

## 6. コンテキストを汚さない工夫

| 工夫 | 効果 |
|---|---|
| **参照を明示する** | 「関係ありそうな文書を探す」フェーズが消える |
| **1タスク＝1セッション** | 前のタスクの文脈が次に混ざらない |
| **`.claudeignore` を置く** | `node_modules`、`cdk.out`、ビルド成果物を検索対象から外す |
| **生成物をリポジトリに置かない** | 静的サイトの出力を `.gitignore` |
| **プロンプト全文は写す** | `10_AIプロンプト設計` の共通ブロックは**要約せずコピーする**。要約すると規則が落ちる |

### プロンプトを要約させない

**`10_AIプロンプト設計` 3.2 の共通ブロックと4章の個別ブロックは、一字一句そのまま実装に写す。**

Claude Code に「要点をまとめて実装して」と言うと、禁止事項や承認の条件が削れる。**これらは削れたことが出力を見ても分からない**種類の規則であり、事故に気づけない。スキル `flourish-ai` の末尾にこの注意を書いてある。

## 7. コストの見積もり

### 1タスクあたり

| 層 | トークン |
|---|---|
| CLAUDE.md ＋ description | **2,090（実測）** |
| スキル1〜2本 | 3,000〜7,000 |
| 参照ドキュメント | 5,000〜15,000 |
| コード（既存ファイルの読み込み） | 5,000〜20,000 |
| **入力の合計** | **15,000〜43,000** |

Sonnet 5（$3/1M）で **1セッションあたり $0.05〜0.13**。**全ドキュメントを読ませる場合の $0.36 と比べて約1/3〜1/7。**

### 全体

62タスク × 平均3セッション（試行錯誤を含む）× $0.10 ≒ **$19**。

**開発期間中のAI利用料は、インフラ固定費（月$13）より小さい。** ここを削る努力より、注意の分散を防ぐ効果のほうが大きい。

## 8. リポジトリ構成（P1-1 で作る）

```text
FlourishStudio/
├── CLAUDE.md                    常時ロード
├── .claude/skills/              5スキル
├── .claudeignore
├── Makefile
├── docs/                        仕様（12本）
├── api/                         FastAPI
│   ├── app/
│   │   ├── api/v1/              ルーター（API設計4章と1対1）
│   │   ├── core/                設定・Cookie・レート制限・エラー
│   │   ├── domain/              業務ルール（件数検証・スコア集計・段階判定）
│   │   ├── ai/
│   │   │   ├── prompts/         プロンプト定義（バージョン付き）
│   │   │   ├── schemas/         出力JSON Schema
│   │   │   └── validators.py
│   │   └── db/                  リポジトリ層
│   ├── tests/
│   └── Dockerfile
├── web/                         Vue 3
│   ├── src/
│   │   ├── styles/tokens.css    デザイントークン
│   │   ├── components/          共通コンポーネント
│   │   ├── views/               画面（S-11.vue など画面IDで命名）
│   │   └── stores/              Pinia
│   └── tests/
├── infra/                       CDK（4スタック）
└── tools/
    ├── generate_site.py         静的サイト生成
    ├── seed_articles.py         記事投入
    └── eval_prompts.py          評価セット実行
```

**`web/src/views/` のファイル名を画面IDにする。** `S-16.vue` と書いてあれば、grep で仕様に辿り着ける。

## 9. 前提が変わったときにやること

| 変わったもの | 更新するもの |
|---|---|
| デザイン原則の色・寸法 | `flourish-ui` **と** `07_デザイン原則`。**両方** |
| APIのエラーコード追加 | `flourish-api` の一覧 **と** `09_API設計` |
| キー設計 | `flourish-data` **と** `08_データモデル` |
| プロンプトのパラメータ | `flourish-ai` **と** `10_AIプロンプト設計` |

**スキルとドキュメントの二重管理になる。** これは意図した代償である。片方だけ直すとスキルが嘘をつくため、**スキルの末尾に必ず出典を書き、迷ったらドキュメントを正とする**運用にしている。

スキルが3回以上嘘をついたら、そのスキルは蒸留しすぎている。**内容を減らして出典への参照を増やす。**
