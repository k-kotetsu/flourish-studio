モノレポは“同じ場所”以上の設計

複数パッケージを置くだけでなく、変更を横断して検査する共通入口を持つことが重要です。Flourish StudioではMakefileがその入口です。

strictを後付けしない

型検査を緩い状態で始めると、既存エラーが増えた後の厳格化が大規模改修になります。最初からmypy strictを採用すると、曖昧な型を新規コードへ持ち込みにくくなります。

lock fileは実行環境の設計図

package-lock.jsonは依存ライブラリの正確な版を固定します。package.jsonが希望、lock fileが実際に入れる組み合わせです。

高速な検査と完全な検査を分ける

pre-commitは開発者の短いフィードバック、CIはクリーン環境での最終判定を担当します。同じ目的でも実行場所と重さが異なります。

最初の工程の成果物は、ユーザー機能ではなく変更を安全に積み重ねられる枠です。ディレクトリをAPI、Web、IaC、toolsへ分けたことで、言語やデプロイ単位の境界がファイル配置から読めます。これは後でチームが増えたときの所有範囲にもなります。

重要なのは、雛形を「空ファイルの集合」で終わらせなかった点です。make lintとmake testが全パッケージを横断し、個別のlint-apiなどへ分解されています。CIはこの個別ターゲットを並列実行でき、開発者は全体ターゲットを一度に呼べます。

一方、雛形コミットは依存関係が多く差分が大きくなりがちです。実務では生成されたlock fileと人が設計した設定ファイルをレビュー上で区別し、pyproject.tomlやtsconfig.jsonの意図を優先して確認します。

Annotated SDK code

SDK・フレームワーク部分をコメント付きで読む

ファイル名：api/pyproject.toml

コメントは処理内容だけでなく、設定理由・失敗時の意味・次工程との接続を説明します。

api/pyproject.tomlPythonの品質SDK／ツール設定を読む · toml
[project]
name = "flourish-api"       # パッケージを識別する名前
requires-python = ">=3.12"  # ローカルとCIが使うPythonの下限

[tool.ruff]
target-version = "py312"   # Python 3.12の構文としてlintする
line-length = 100           # formatter/linterの共通折返し幅

[tool.ruff.lint]
# E/F: 基本エラー、I: import順、UP: 新しい構文、B: bugbear、SIM: 単純化
select = ["E", "F", "I", "UP", "B", "SIM"]

[tool.mypy]
python_version = "3.12"
packages = ["app", "tests"] # 製品コードだけでなくテストも型検査する
strict = true               # 暗黙のAnyなどを許しにくくする
warn_unused_ignores = true  # 不要になった型エラー抑制を検出する
教材用コメントを追加した抜粋です。実ファイルは同名の設定をコメント少なめで保持します。

Hands-on runbook

同じ作業を手動で行う手順書

この工程にAWS Management Console操作はありません。ローカル端末で同じ雛形を組み、Gitの最初の履歴として確定します。GUIクライアントを使ってもよいですが、実行されるGit操作は同じです。

i
先に名前と対象環境を固定する

画面操作を始める前に、AWSアカウントID・リージョン・環境名・作業対象リソースをメモします。コンソールの既定値は更新されることがあるため、現在値を読み取ってから確定してください。

  1. 前提をそろえる

    Git、Python 3.12、Node.js 22、Dockerをインストールし、各バージョンを表示します。想定より新旧がずれる場合は先に合わせます。

    期待結果：各コマンドがエラーなく版番号を返す

  2. ディレクトリ境界を作る

    リポジトリ直下へ api、web、infra、tools、docs を用意します。生成ツールを使う場合も、配置先がこの境界を越えていないか確認します。

    期待結果：各パッケージの設定が自分の配下にある

  3. 依存関係と品質設定を固定する

    Pythonはpyproject.toml、Node系はpackage.jsonとlock file、全体はMakefileとpre-commit設定を作ります。秘密情報と生成物は.gitignoreへ追加します。

    期待結果：makeの各個別ターゲットが存在する

  4. クリーン状態からセットアップする

    make setupを実行します。既存キャッシュで偶然通らないよう、可能なら別ディレクトリへのcloneでも同じ操作を試します。

    期待結果：api/.venvとnode_modulesが再現される

  5. 品質ゲートを通す

    make lintとmake testを実行し、失敗したツール名とファイルを読み取ります。検査を無効化して通さないでください。

    期待結果：すべて終了コード0

  6. 最初のコミットを作る

    git statusで秘密情報や生成物が含まれていないことを見てから、タスクIDと目的を含むメッセージでコミットします。

    期待結果：差分が雛形と仕様書だけで説明できる

STEP 01

2. P1-1 リポジトリの雛形を作る#

この工程の目的#

開発者全員が同じディレクトリ構成、同じコマンド、同じ品質基準で作業できる状態を作ることです。本機能を作る前に、「コードを置く場所」と「間違いを早く見つける仕組み」を用意しました。

  • 対象コミット：3ec971c
  • 完了条件：make lintが通る
  • 主な成果：api/↗、web/↗、infra/↗、tools/↗、Makefile↗、静的解析設定、pre-commit設定、設計ドキュメント

2.1 4つのパッケージへ責務を分けた#

ディレクトリ言語・技術責務
api/↗Python 3.12HTTP API、ドメインロジック、DBアクセス、AI呼び出し
web/↗Vue 3 + TypeScriptブラウザで動くSPA
infra/↗TypeScript + AWS CDKAWSリソースの定義
tools/↗Python 3.12運用時に手元やCIで実行するスクリプト

重要なのは、技術ではなく責務で分けている点です。APIコードとインフラコードを同じ場所へ混ぜると、依存関係やテスト対象が分かりにくくなります。

2.2 Pythonの品質基準を設定した#

api/pyproject.toml↗では、Ruffとmypyを厳しめに設定しています。

toml 
[tool.ruff]
target-version = "py312"
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM"]

[tool.mypy]
python_version = "3.12"
packages = ["app", "tests"]
strict = true
  • Ruff：未使用import、書式、よくあるバグなどを機械的に検出するリンター
  • mypy：型ヒントを使い、実行前に型の矛盾を検出する静的型チェッカー
  • strict：曖昧な型を許しにくくする厳格モード

たとえば、戻り値がstrのはずなのにNoneを返すコードは、実際にその経路を動かす前に見つけられる可能性が高まります。

2.3 フロントエンドとインフラにも同じ考え方を適用した#

フロントエンドはESLintとvue-tsc、インフラはESLintとTypeScriptコンパイラで検査します。

json 
{
  "scripts": {
    "lint": "eslint .",
    "typecheck": "vue-tsc -b --noEmit"
  }
}

--noEmitは、JavaScriptファイルを生成せず、型検査だけを行う指定です。Vueの.vueファイルは通常のtscだけでは十分に検査できないため、vue-tscを使います。

2.4 Makefileでコマンドを統一した#

ルートのMakefile↗は、複数言語のコマンドを隠蔽し、開発者が共通の入口を使えるようにします。

make 
setup: setup-api setup-tools setup-web setup-infra

lint: lint-api lint-tools lint-web lint-infra

test: test-api test-web test-infra

後続工程で中身は増えましたが、「全体」「APIだけ」「Webだけ」の入口を用意する構造はP1-1で決まりました。

よくある実務上の工夫：READMEに長いコマンドを書くより、make testのような短い標準コマンドを用意すると、ローカルとCIで同じ手順を再利用できます。

2.5 pre-commitでコミット前に検査した#

.pre-commit-config.yaml↗には次のような検査が定義されています。

  • 行末の余分な空白
  • ファイル末尾の改行
  • YAML/JSONの構文
  • マージコンフリクトの消し忘れ
  • 大きすぎるファイル
  • 各パッケージのlintと型検査

pre-commitは、git commitの直前に自動で処理を走らせる仕組みです。CIに送ってから単純ミスへ気づくより、手元で数秒以内に気づくほうが修正コストを下げられます。

2.6 .gitignore↗で生成物や秘密情報を除外した#

gitignore 
.venv/
node_modules/
dist/
cdk.out/
.env
.env.*
  • .venv/やnode_modules/は依存パッケージの展開先であり、ソースコードではない
  • dist/やcdk.out/はソースから再生成できる
  • .envには秘密情報が入る可能性がある

重要：.gitignore↗は、すでにGitへ登録した秘密情報を消す仕組みではありません。誤ってコミットした場合は、値を無効化・再発行したうえで履歴への対応を検討する必要があります。

2.7 この工程で行った確認#

  • 各パッケージの依存関係を導入できること
  • make lintが通ること
  • 最小のプレースホルダーテストが実行できること
  • 設計書と開発規則をリポジトリへ含めること

用語メモ#

  • 雛形／scaffold：機能本体を実装する前のディレクトリや設定の土台
  • lint：コードを実行せず、書き方や潜在的な誤りを検査すること
  • 静的型検査：実行前に型の整合性を調べること
  • 依存関係：アプリが利用する外部ライブラリや別モジュール
  • モノレポ：複数のアプリやパッケージを1つのリポジトリで管理する方式

この工程から学べる開発の定石#

最初の工程で品質チェックを置くと、その後に追加されるすべてのコードが同じ基準を通ります。品質基準を後付けすると、既存コードの大量修正が必要になるため、雛形の時点で導入する価値があります。
