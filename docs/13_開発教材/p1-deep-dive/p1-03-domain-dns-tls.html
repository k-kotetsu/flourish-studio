ドメイン登録とホストゾーンは別の役割

登録は名前の利用権、ホストゾーンはその名前のDNSレコード管理です。Route 53で同時に用意されることがありますが、概念を分けると移管時にも迷いません。

証明書は名前と秘密鍵の管理

ACM公開証明書は、ドメインを管理していることをDNS等で検証して発行されます。アプリへ秘密鍵を配るのではなく、CloudFrontがACM証明書を利用します。

apexとwildcardは包含関係ではない

*.flourish-st.comはdev.flourish-st.comを覆いますが、flourish-st.com自体は覆いません。そのため両方をSANへ入れます。

リージョンは参照可能性を決める

CloudFront用ACM証明書はus-east-1へ置きます。APIやDynamoDBを東京へ置いても、エッジ側の証明書とWAFは別リージョンになります。

P1-3にはアプリケーションコードの追加がありません。しかし後続のP1-7は、ドメイン、Route 53ホストゾーン、us-east-1でISSUEDになった証明書がなければ完成しません。このような外部状態を作る工程も、完了条件と識別子をGitへ記録することで追跡可能にします。

DNS検証ではACMが提示するCNAMEレコードをRoute 53へ追加します。検証用レコードは発行後も残すのが基本です。ACMの管理更新時に同じレコードを使えるためです。証明書がPending validationのままなら、リージョン、CNAME名の二重ドメイン付与、ネームサーバー委任を順に確認します。

手動資産はCloudFormationの所有外です。CDKスタックを削除してもドメインや証明書は消えません。これは保護になる一方、環境ごとの棚卸しと更新期限・請求の管理責任が残ることを意味します。

AWS Management Console
i
先に名前と対象環境を固定する

画面操作を始める前に、AWSアカウントID・リージョン・環境名・作業対象リソースをメモします。コンソールの既定値は更新されることがあるため、現在値を読み取ってから確定してください。

  1. AWSアカウントと請求先を確認する

    AWS Management Consoleへ管理者相当ではなく作業用IAM Identity Center権限で入り、アカウントIDと請求アラームを確認します。

    期待結果：対象アカウントを取り違えていない

  2. ドメインを登録または委任する

    Route 53 → Registered domainsからflourish-st.com相当を登録します。外部レジストラを使う場合は、Route 53でpublic hosted zoneを作り、表示されたNSをレジストラへ設定します。

    期待結果：public hosted zoneが1つありNSが委任済み

  3. ACMをus-east-1へ切り替える

    画面右上のリージョンをUS East (N. Virginia) us-east-1へ変更してCertificate Managerを開きます。東京リージョンに作らないでください。

    期待結果：ACM画面のリージョンがus-east-1

  4. 公開証明書をリクエストする

    Request certificate → Public certificateを選び、apexとwildcard（例：flourish-st.comと*.flourish-st.com）を追加し、DNS validationを選びます。

    期待結果：2つの名前が証明書詳細へ表示される

  5. DNS検証レコードを作る

    証明書詳細のCreate records in Route 53を使うか、提示されたCNAMEを対象hosted zoneへ追加します。レコード名を手入力するときはゾーン名を二重付与しないよう確認します。

    期待結果：両ドメインのValidation statusがSuccess

  6. ISSUEDと識別子を記録する

    証明書statusがISSUEDになるまで待ち、certificate ARN、hosted zone ID、zone name、対象ドメイン、リージョンを秘密値を含めずbacklogへ記録します。

    期待結果：後続CDKに必要な4情報が揃う

STEP 03

4. P1-3 ドメイン、DNS、TLS証明書を準備する#

この工程の目的#

ユーザーがアクセスする名前と、HTTPS通信に必要な証明書を用意することです。この工程は主にAWSコンソールなどの外部操作であり、アプリケーションコードの追加ではありません。

  • 対象コミット：d6d75e8
  • 実施者：人
  • 記録された結果：flourish-st.com取得、Route 53ホストゾーン作成、us-east-1のACM証明書がISSUED
  • コード上の成果：技術構成とバックログへの完了記録

4.1 ドメインとDNSの役割#

ブラウザはdev.flourish-st.comという文字列だけでは接続先を知りません。DNSが、その名前をCloudFrontなどの接続先へ結び付けます。

このリポジトリでは後続のP1-7で、Route 53にCloudFront向けのAliasレコードを作ります。

ts 
new route53.ARecord(this, "AliasRecord", {
  zone: hostedZone,
  recordName: props.domainName,
  target: route53.RecordTarget.fromAlias(
    new targets.CloudFrontTarget(this.distribution),
  ),
});

P1-3はこのコードが参照するホストゾーンとドメインを、先に人が準備した工程です。

4.2 ACM証明書をus-east-1へ置く理由#

CloudFrontで独自ドメインのHTTPSを使う場合、ACM証明書はus-east-1リージョンに必要です。一方、APIやDynamoDBは主にap-northeast-1に置きます。

この制約が、P1-7でEdgeStackをus-east-1へ、AppStackをap-northeast-1へ分ける理由になります。

4.3 証明書の対象#

記録では、apexのflourish-st.comとワイルドカードの*.flourish-st.comを対象にした証明書が作成されています。

  • apexドメイン：flourish-st.comのように、前にサブドメインがない名前
  • ワイルドカード証明書：*.flourish-st.comのように複数のサブドメインを対象にする証明書
  • ISSUED：証明書が発行済みで利用可能な状態

4.4 コードを書かない工程もコミットする意味#

外部サービスの操作結果を記録しないと、後から見た人は次のことを判断できません。

  • 誰がどこまで作業したか
  • 証明書はどのリージョンにあるか
  • どのドメイン名をコードで参照すべきか
  • 後続タスクの依存条件が満たされたか

そこでP1-3では、tech-architecture.mdとbacklog.mdを変更し、外部状態をリポジトリの履歴へ残しました。

用語メモ#

  • DNS：ドメイン名を接続先へ変換する仕組み
  • Route 53：AWSのDNSサービス
  • ACM：AWS Certificate Manager。TLS証明書を管理するサービス
  • TLS/HTTPS：通信を暗号化し、接続先を証明する仕組み
  • リージョン：AWSの地理的な提供地域
  • ホストゾーン：Route 53で、あるドメインのDNSレコード群を管理する単位

この工程から学べる開発の定石#

コード外の作業も、完了条件と結果を文書化します。特にリージョン、リソース名、手動投入した秘密情報の「保存先」は、後続のIaCと運用に影響します。ただし秘密情報の値そのものはGitに書きません。
