workflow・job・step

workflowは1ファイルの自動化、jobは独立した実行環境、stepはjob内の順番です。P1-2ではAPI/Web/infra/toolsを別jobにして並列化しました。

CIとCDの責務

CIは変更が安全かを判定し、CDは成果物を環境へ反映します。この時点のdeployコマンドはプレースホルダーなので、“配線を作った”ことと“本番配信できる”ことを分けます。

Environmentは秘密と承認の境界

production Environmentをjobへ指定すると、承認ルールと環境secretをそのjobだけへ適用できます。YAMLだけでなくGitHub設定画面側の構成も必要です。

最小権限を明記する

workflowのpermissionsは将来AWS OIDCを追加するときにも重要です。暗黙の既定権限に頼らず、必要な権限だけを宣言するのが安全です。

pull_requestとpushは同じコミットを対象にしても意味が違います。PR時点ではマージ可否を判断し、mainへ入った後は共有dev環境を更新する契機になります。本番はさらにv*タグと人の承認を要求し、事故の半径を小さくします。

各jobが毎回新しいrunnerで始まる点も大切です。ローカルPCに残った依存や環境変数に依存しているコードは、Actions上で失敗します。これは面倒ではなく、再現性の欠如を早期に見つける仕組みです。

現在のmake deploy-devとprodの最終stepは未実装です。深掘りでは、ワークフローが緑でもAWSへ反映されたとは限らないという読み方を維持します。

Annotated SDK code

SDK・フレームワーク部分をコメント付きで読む

ファイル名：.github/workflows/ci.yml

コメントは処理内容だけでなく、設定理由・失敗時の意味・次工程との接続を説明します。

.github/workflows/ci.ymlGitHub Actionsのworkflow構文 · yaml
name: CI                         # Actions画面に表示するworkflow名

on:
  pull_request:
    branches: [main]             # main向けPRだけを品質ゲートにする

permissions:
  contents: read                # checkoutに必要な読み取りだけを許可

concurrency:
  group: ci-${{ github.ref }}    # 同じPRの古い実行を同一グループにする
  cancel-in-progress: true       # 新しいpush時に古い検査を止める

jobs:
  api:                          # jobごとに独立runnerが起動する
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12" # ローカル設定と版を合わせる
      - run: make setup-api      # Makefileを唯一の手順入口にする
      - run: make lint-api
      - run: make test-api

  # web / infra / toolsも別jobにすると、失敗箇所が明確で並列実行できる

Hands-on runbook

同じ作業を手動で行う手順書

workflow本体はコードとして管理しますが、Actions許可、branch protection、production Environmentの承認者はGitHubのWeb画面で設定します。画面名はGitHubの更新で多少変わることがあります。

GitHub Web Console
i
先に名前と対象環境を固定する

画面操作を始める前に、AWSアカウントID・リージョン・環境名・作業対象リソースをメモします。コンソールの既定値は更新されることがあるため、現在値を読み取ってから確定してください。

  1. Actionsの利用可否を確認する

    GitHubのRepository → Settings → Actions → Generalを開き、組織ポリシー内で必要なActionsを許可します。外部Actionは信頼できる提供元と固定版を選びます。

    期待結果：Actionsタブでworkflowを認識できる

  2. workflowファイルを配置する

    .github/workflows/にci.yml、deploy-dev.yml、deploy-prod.ymlをcommitし、Actionsタブで構文エラーがないことを見ます。

    期待結果：3つのworkflow名が一覧に現れる

  3. mainの保護ルールを作る

    Settings → Rules → Rulesets（またはBranches）でmainを対象に、Pull request必須・必要なstatus checks必須・直接push禁止を設定します。

    期待結果：保護対象にmainが表示される

  4. production Environmentを作る

    Settings → Environments → New environmentでproductionを作り、Required reviewersと必要ならdeployment branchを設定します。

    期待結果：prod jobが承認待ちで停止できる

  5. PRでCIを確認する

    小さな変更でPRを作り、ActionsまたはPRのChecksからapi/web/infra/toolsのログを開きます。意図的なlint違反を一時的に入れるとゲートの失敗も確認できます。

    期待結果：4 jobが判定され、失敗時はmerge不可

  6. devとprodのトリガーを確認する

    main mergeでdev workflow、テスト用vタグでprod workflowが開始されることを確認します。現段階のdeploy stepはプレースホルダーであることもログで確認します。

    期待結果：トリガーは動くがAWS更新はしない

STEP 02

3. P1-2 GitHub ActionsでCI/CDの流れを作る#

この工程の目的#

ローカルでしか実行されないチェックを、GitHub上でも自動実行することです。また、mainへの反映と本番タグをデプロイのきっかけにする枠組みを作りました。

  • 対象コミット：a215230
  • 主なファイル：.github/workflows/ci.yml↗、deploy-dev.yml、deploy-prod.yml
  • 完了条件：Pull RequestでCIが成功する

3.1 PRごとに4つのジョブを並列実行した#

yaml 
on:
  pull_request:
    branches: [main]

jobs:
  api:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: make setup-api
      - run: make lint-api
      - run: make test-api

実際のci.ymlにはapi↗、tools↗、web↗、infra↗の4ジョブがあります。互いに独立したジョブにすると、次の利点があります。

  • 実行できる環境では並列化され、全体が早く終わる
  • どの層で失敗したかが一目で分かる
  • Pythonだけ、Nodeだけという実行環境を個別に設定できる

3.2 lock fileを使って同じ依存関係を入れた#

Node系ではnpm installではなくnpm ciを使います。

yaml 
- uses: actions/setup-node@v4
  with:
    node-version: "22"
    cache: npm
    cache-dependency-path: web/package-lock.json
- run: make setup-web

npm ciはpackage-lock.jsonを基準に、再現性の高いインストールを行います。開発者のPCとCIで異なるバージョンが入り、片方だけ失敗する状況を減らせます。

3.3 devとprodのトリガーを分けた#

ワークフロー起動条件意図
CImain向けPull Requestマージ前の検査
Deploy devmainへのpush開発環境を最新化
Deploy prodv*タグのpush明示した版だけ本番反映

本番用ジョブには次の設定があります。

yaml 
environment: production

GitHub側のEnvironmentにRequired reviewersを設定すれば、タグを作っただけでは本番デプロイせず、人の承認を挟めます。

3.4 この段階の「デプロイ」は枠組みだけだった#

ここは重要です。P1-2ではワークフローを作りましたが、現在のMakefile↗でもmake deploy-devは次のプレースホルダーです。

make 
deploy-dev:
	@echo "未実装（P1-6: AppStack、P1-7: EdgeStack を参照。cdk deploy に置き換える）"

本番ワークフローも実際のcdk deployではなくメッセージ出力です。つまり、CDのトリガーと承認経路はあるが、デプロイ本体は未完成です。

教材では「ワークフローのファイルがある」ことと「実際にデプロイできる」ことを混同してはいけません。

用語メモ#

  • CI（Continuous Integration）：変更のたびにビルド・lint・テストを自動実行する考え方
  • CD（Continuous Delivery/Deployment）：検証済みの変更を環境へ届ける仕組み
  • Pull Request／PR：変更内容をレビューし、ブランチへ取り込むための単位
  • workflow：GitHub Actionsで自動実行する処理の定義
  • job / step：workflow内の実行単位。jobの中に複数のstepがある
  • タグ：特定コミットにv1.0.0などの名前を付けるGitの機能

この工程から学べる開発の定石#

CIでは、ローカルと異なる独自コマンドを増やさず、make lintやmake testを再利用します。「手元では通るのにCIでは別手順」という差を小さくすることが、安定した開発につながります。
