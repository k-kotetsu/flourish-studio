工程コミット 02fec8a で追加した意図を中心に説明し、コード例は main @ a9b388e の現行形へ教材用コメントを加えています。後続工程で変わった部分は元教材の章と照合してください。

User PoolとIdentity Poolを混同しない

この工程は認証ユーザーを管理するUser Poolです。AWSサービス用一時credentialをブラウザへ渡すIdentity Poolではありません。

authorization code grant

ブラウザには短命なcodeだけを戻し、バックエンドがclient secretを使ってtokenへ交換します。tokenをブラウザ保管しないBFF方針と整合します。

GoogleとCognitoのredirect URIは2種類

GoogleにはCognitoの/oauth2/idpresponseを登録し、Cognito app clientには自サービスの/auth/google/callbackを登録します。向きを混ぜるとredirect mismatchになります。

SecretValueは値を埋め込まない

CDKはSecrets Managerの参照をCloudFormationへ渡します。client secret実値をソース、context、output、ログへ出しません。

認証フローにはブラウザ、FlourishのBFF、Cognito、Googleの4者が登場します。Googleで本人確認した結果はCognitoへ戻り、Cognitoが統一したcodeをFlourishへ返します。Flourishのバックエンドがcodeをtokenへ交換し、最終的には独自のfs_session Cookieを発行する設計です。

generateSecret: trueのapp clientは秘密を保持できるサーバー向けです。SPAからCognitoへ直接token交換するとclient secretを安全に隠せないため、この設定と矛盾します。フロントは同一originのBFF APIだけを呼びます。

Cognitoの標準メール確認を無効にしている点も仕様上重要です。確認処理を独自フローで行う前提なので、コンソールで作り直すときに既定の自動検証をそのまま有効にすると、ユーザー体験とAPI契約が変わります。

infra/lib/auth-stack.tsCognitoとSecrets ManagerのCDK Construct · typescript
// Secret Constructは保管場所だけをIaCで作り、値はAWS Consoleから手動投入する。
this.googleOAuthClientSecret = new secretsmanager.Secret(this, "GoogleOAuthClientSecret", {
  secretName: "flourish/google-oauth-client-secret",
  description: "Google OAuth client secret. Value is entered manually.",
});

// Google IdP SDKはGoogleのclient IDとsecret参照をUser Poolへ関連付ける。
const googleIdp = new cognito.UserPoolIdentityProviderGoogle(this, "GoogleIdentityProvider", {
  userPool: this.userPool,
  clientId: props.googleClientId,             // 公開情報なのでpropsで渡せる
  clientSecretValue: cdk.SecretValue.secretsManager(
    this.googleOAuthClientSecret.secretArn,   // 実値ではなくARN参照
  ),
  scopes: ["openid", "email", "profile"],  // Googleから必要な属性だけ要求
  attributeMapping: { email: cognito.ProviderAttribute.GOOGLE_EMAIL },
});

// BFFがcodeを交換するため、secret付きclient + code grantにする。
this.userPoolClient = this.userPool.addClient("UserPoolClient", {
  generateSecret: true,
  oAuth: {
    flows: { authorizationCodeGrant: true },
    scopes: [cognito.OAuthScope.OPENID, cognito.OAuthScope.EMAIL, cognito.OAuthScope.PROFILE],
    callbackUrls: [`https://${props.domainName}/auth/google/callback`],
  },
  supportedIdentityProviders: [
    cognito.UserPoolClientIdentityProvider.COGNITO,
    cognito.UserPoolClientIdentityProvider.GOOGLE,
  ],
});
this.userPoolClient.node.addDependency(googleIdp); // IdP作成後にclientを作る順序を保証

同じ作業を手動で行う手順書

2つの管理画面を往復します。secret値はコピー時だけ扱い、教材、issue、スクリーンショット、Gitへ残さないでください。既存secretを更新する場合は利用中versionへの影響を確認します。

Google Cloud + AWS Console
i
先に名前と対象環境を固定する

画面操作を始める前に、AWSアカウントID・リージョン・環境名・作業対象リソースをメモします。コンソールの既定値は更新されることがあるため、現在値を読み取ってから確定してください。

  1. Google OAuth clientを作る

    Google Cloud Console → APIs & Services → CredentialsでOAuth client ID（Web application）を作ります。Authorized redirect URIは後で得るCognitoの/oauth2/idpresponseです。

    期待結果：client IDとclient secretを一度だけ安全に取得

  2. User Poolを作る

    Amazon Cognito → User pools → Create user pool。email sign-in、self sign-up、必須email、8文字以上で英小文字と数字必須、recoveryはemailを選びます。

    期待結果：flourish-users相当のpoolがActive

  3. Cognito domainを設定する

    User pool → Branding/Domainから一意なprefix（例 flour​​ish-st-dev）を設定し、表示されたdomainを記録します。

    期待結果：managed login domainが有効

  4. Secrets Managerへsecretを保存する

    Secrets Manager → Store a new secret → Other typeでGoogle client secretを保存し、名前をflourish/google-oauth-client-secretにします。閲覧権限を最小化します。

    期待結果：secret ARNがあり値をGitへ置いていない

  5. Google IdPを追加する

    User pool → Social and external providers → Add identity provider → Googleでclient ID/secret、scope openid email profile、email mappingを設定します。

    期待結果：Google providerがEnabled

  6. app clientを設定する

    App clientsでconfidential clientを作り、authorization code grant、openid/email/profile、callback https://dev.flourish-st.com/auth/google/callback、CognitoとGoogle providerを有効にします。

    期待結果：client secretあり・implicit grantなし

  7. Google側redirectを確定する

    Cognitoのdomainからhttps://PREFIX.auth.REGION.amazoncognito.com/oauth2/idpresponseを組み、Google OAuth clientのAuthorized redirect URIへ正確に登録します。

    期待結果：末尾パスまで完全一致

  8. managed loginで往復を確認する

    App clientのView login pageまたはauthorize URLを開き、Google選択後にFlourish callbackまでcodeが戻ることを確認します。P1時点でcallback APIが未実装なら404でもcode付与までを確認します。

    期待結果：redirect_uri_mismatchが発生しない

6. P1-5 CognitoのAuthStackを作る#

この工程の目的#

メールアドレス・パスワードとGoogleログインを扱うユーザーディレクトリを用意し、秘密情報をコードから分離することです。

  • 対象コミット：02fec8a
  • 主なファイル：infra/lib/auth-stack.ts↗、infra/test/auth-stack.test.ts↗、infra/bin/infra.ts↗
  • 人の作業：Google CloudでOAuthクライアントを作成し、実シークレットをSecrets Managerへ投入
  • 実機確認：ap-northeast-1へデプロイし、Google IdPとUser Pool Clientを確認済み

6.1 Cognito User Poolを定義した#

ts 
this.userPool = new cognito.UserPool(this, "UserPool", {
  userPoolName: "flourish-users",
  selfSignUpEnabled: true,
  signInAliases: { email: true },
  standardAttributes: {
    email: { required: true, mutable: true },
  },
  passwordPolicy: {
    minLength: 8,
    requireLowercase: true,
    requireUppercase: false,
    requireDigits: true,
    requireSymbols: false,
  },
  accountRecovery: cognito.AccountRecovery.EMAIL_ONLY,
  removalPolicy: cdk.RemovalPolicy.RETAIN,
});

User Poolは、ユーザーのアカウントを管理するCognitoの機能です。このサービスでは電話番号を収集しないため、アカウント復旧もメールだけにしています。

パスワードポリシーは「8文字以上、英字と数字」を表現しています。ただし、よく使われる流出パスワードの拒否はCognitoのこの設定だけでは実現できないため、後続のバックエンド実装へ残しています。

6.2 GoogleをIdentity Providerとして追加した#

ts 
const googleIdp = new cognito.UserPoolIdentityProviderGoogle(
  this,
  "GoogleIdentityProvider",
  {
    userPool: this.userPool,
    clientId: props.googleClientId,
    clientSecretValue: cdk.SecretValue.secretsManager(
      this.googleOAuthClientSecret.secretArn,
    ),
    scopes: ["openid", "email", "profile"],
    attributeMapping: {
      email: cognito.ProviderAttribute.GOOGLE_EMAIL,
    },
  },
);
  • IdP（Identity Provider）：ユーザーの本人確認を行う提供者
  • OAuth 2.0：別サービスの認可を安全に委譲する仕組み
  • OpenID Connect：OAuth 2.0の上でログイン情報を扱う仕組み
  • scope：取得を許可してもらう情報の範囲

ts 
this.googleOAuthClientSecret = new secretsmanager.Secret(

クライアントIDは公開されても認証の突破には直結しない識別子ですが、クライアントシークレットは秘密です。コードには「Secrets Managerのどの秘密を参照するか」だけを書き、値は外部から手動投入しました。

6.4 認可コードフローとBFF方式#

ts 
this.userPoolClient = this.userPool.addClient("UserPoolClient", {
  generateSecret: true,
  oAuth: {
    flows: { authorizationCodeGrant: true },
    callbackUrls: [`https://${props.domainName}/auth/google/callback`],
  },
});

このリポジトリはBFF（Backend for Frontend）方式を採用しています。CognitoのトークンをブラウザのJavaScriptへ直接持たせず、バックエンドが認証結果を受け取り、ブラウザには独自のセッションCookieを発行します。Cookieとセッションの実装はP1-11で行います。

6.5 CDKテストで確認したこと#

  • パスワードが8文字以上で英字・数字を要求する
  • 復旧手段がメールのみ
  • Cognito Hosted Domainがある
  • User Pool Clientが認可コードフローとシークレットを持つ
  • Google用Secrets Managerリソースがある
  • User PoolがRETAINされる

用語メモ#

  • Cognito：AWSのユーザー管理・認証サービス
  • BFF：特定のフロントエンドのために認証やAPI統合を担うバックエンド
  • 認可コードグラント：ブラウザへ直接アクセストークンを露出しにくいOAuthフロー
  • callback URL：外部ログイン後に戻るURL
  • Secrets Manager：APIキーやパスワードなどの秘密を安全に保存するAWSサービス
  • Cognito Hosted Domain：Cognitoが提供するログイン処理用ドメイン

この工程から学べる開発の定石#

認証では「ログインできること」だけでなく、トークンや秘密情報をどこに置くかが重要です。公開してよい識別子と、漏れてはいけないシークレットを区別し、後者をソース管理から外します。
